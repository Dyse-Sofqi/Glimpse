# Changelog

#### 1.1.4 (2026-10-05)

**Fixes**

- **Fixed "the teleprompter toolbar wraps after switching document tabs and only heals ~1 s later"**: two parts of the toolbar width floor were fragile. **First**, `raiseToMinWidth()` decided "is the floor already met?" from `state.width`, which can disagree with the width actually rendered: once the state is the larger of the two it returns early and never fixes a too-narrow DOM, leaving the wrap until the once-per-second reconciliation's `autoFitWidth()` wrote the width back (which is exactly the "heals by itself after ~1 s" the user saw, mistaken for a second hover). The decision is now made on the **rendered width (`rootEl.offsetWidth`)**, so state/rendering disagreements are corrected immediately. **Second**, the floor was only re-measured at a few call sites (bind-name change, mode label, click-through lock, width lock), so any event-ordering mismatch skipped it. A **toolbar ResizeObserver** now re-applies the floor within the **same frame** whenever the toolbar itself or the bind button changes size (wrapping, renaming, font metrics) — its callback runs after layout and before paint, so a wrap is never painted and no "flash" is visible. Finally, the toolbar's single-line width is now measured by **summing the visible items' laid-out geometry** instead of "temporarily unwrap, measure, restore" (wrapping only decides which line each item lands on, it does not change item widths), so measuring no longer mutates the live toolbar's inline styles and no longer depends on whether it happens to be wrapped
  - Verification: 3 new regression assertions (37 across both suites, all passing) — switching document tabs to a longer name keeps the toolbar on one row with the window width following the floor; **forcing the DOM below the floor while `state.width` stays larger** (the failure class) heals to one row within the same frame; and the floor measured while the toolbar is wrapped equals the unwrapped measurement

#### 1.1.3 (2026-10-05)

**New features**

- **Teleprompter lyrics-extract mode: double-click the text area to play/pause the current song**: in lyrics mode, double-clicking the teleprompter body plays the current song, and a second double-click pauses it (watch the lyrics, double-click, and it plays — no trip to the music panel). Toggling and feedback live in `MusicManager.toggleCurrentSong()`: playing → pause (via `audio.pause()`, the same chain as the panel button: pause event → player callback → `emitState`); paused → resume (if `audio.play()` produces no sound it points you at the music panel's play button, the same handling as the preview chain); no current song → "not playing" notice (matching the lyrics mode placeholder); a loaded song whose audio never attached (decode failure / no playable source) → "current song not ready". Its only difference from the `toggleActivePlayer()` used by the panel button and the command is the feedback — that one is a bare toggle that stays silent with nothing loaded, whereas a double-click on the teleprompter text area is the one gesture with no button affordance, so it must speak up when there is nothing to play or playback is refused. Every other mode keeps jumping the cursor to the captured line (`jumpToCapturedLine`'s lyrics branch is now dispatched by `handleContentDblClick()`)
- **Starting a preview now jumps to the lyrics pane and auto-matches lyrics**: when an online song starts auditioning, the panel switches straight to the lyrics pane exactly like playing a local song, showing a "loading preview …" status first (the tab progress bar lives in the songs pane and would be hidden after the switch, so the same feedback is given in the lyrics pane); once it starts playing, the existing **empty-lyrics auto-match** takes over: a four-platform search on "title + artist" → the first candidate that has lyrics → mounted **temporarily** onto the preview player via `applyPreviewLyrics` (valid for this audition only, nothing written to disk; if no candidate has lyrics the manual candidate list is shown instead). A failed or superseded audition clears that status along with `stopPreview()`. Previously a preview never switched panes, so auto-matching only happened if you manually switched to the lyrics pane
- **Audition (streamed) rows now share the local rows' play/pause cover overlay**: while an online song is being auditioned, the cover overlay no longer shows a "stop audition" square — it shows the exact same **pause icon** as local songs, and a second click pauses, a third resumes (the player and its blob are kept, so resuming never re-fetches). **The backdrop is now the same "darkened cover" as local rows too** (`rgba(0,0,0,.45)`, `.62` on hover) instead of a solid accent colour — hovering or pausing an audition row just dims the cover; the only difference from a local row is that the overlay stays visible without hovering, which remains the "this row is auditioning" marker. Pause/resume is synced to the overlay from state pushes, so a pause from the bottom bar, a shortcut or the queue advancing all land on the right icon (icons are only re-set when the play state actually flips — `timeupdate` pushes several times a second without rebuilding the SVG). The hand-over/reset logic is unchanged (switching songs, playing something else or the queue advancing moves or clears it). The previous behaviour was "click again to stop and destroy the player", so pausing an audition is new

**Fixes**

- **Fixed the teleprompter toolbar being split across two or three rows**: in a narrow window the hover toolbar's 12 controls (doc binding, mode dropdown + 10 icon buttons) were folded by `flex-wrap` into two or three rows with only a couple of buttons each, so every click meant hunting for the control again. Root cause: the minimum width was the fixed constant `240px`, unrelated to the toolbar's actual single-line natural width (≈470px on this machine, varying with the bound document name and mode label).
  - **The toolbar's single-line width is now the window minimum width**: new `minWidth()` = `max(240px, toolbar single-line natural width + 4px sub-pixel buffer)`, capped at the viewport width and applied uniformly by `clampWidth()` — width auto-fit, right-edge dragging and width lock all respect it, so the window can no longer be narrow enough to wrap the toolbar
  - **How it is measured**: measuring the toolbar as-is doesn't work — an already-wrapped toolbar is clamped to the window width by `max-width:100%`, so the measurement returns the wrapped width (using it as a minimum would freeze the current state). Measurement now temporarily applies `nowrap + max-content + no width cap`, reads `offsetWidth` (forcing a synchronous layout) and restores the styles in the same frame (the transient state is never painted), yielding the true single-line natural width
  - **The floor is re-applied wherever the toolbar's composition or labels change** (new `raiseToMinWidth()`, raise-only): the bind button shows the active document name, the mode label follows the mode, and click-through lock keeps only the interactive buttons — all three change the single-line width. During construction `setWidthLocked()` runs before `updateBindBtn()`/`updateModeSelect()` (the bind button still shows "—" and the mode label is empty), so a restored width-locked window can only pick up the real floor at those change points; otherwise it stayed at the too-small floor and kept wrapping
  - **Width lock still locks the width, but not below the floor**: locking means "does not follow content", not "may be narrow enough to wrap the toolbar"; a locked width below the floor in an old data.json is raised to the floor on restore (content-driven re-layout is still skipped, and the user's chosen width is never shrunk)
  - **Click-through lock measures only the currently visible buttons**: while locked the toolbar keeps just prev/next/click-through-lock (floor falls back to the 240px constant), so a locked desktop-lyrics style narrow window is not stretched to the unlocked width; unlocking restores the full floor
  - **When the viewport is narrower than the toolbar**: the window falls back to the viewport width (never overflows the screen); wrapping is unavoidable in that extreme case
- **Fixed the text area still intercepting the mouse while click-through locked**: 1.1.2 made the window root permanently `pointer-events: none` and gave the visible panel (`.glimpse-tp-body`, which contains the text) `auto` — the intent was that a drifted transparent area never blocks the editor, but **an explicit `auto` on a child puts it back into hit-testing**, so `none` on the root cannot stop it: while locked the text area still swallowed clicks (blocking selection/editing, and still firing double-click-to-jump and right-click-to-copy; the new double-click playback control would have misfired the same way). Added `.glimpse-teleprompter.is-locked .glimpse-tp-body { pointer-events: none }`, restoring the "whole window passes clicks through, only the interactive buttons remain" behaviour documented in the ADR/README; the toolbar's own rule already sets `pointer-events: auto`, so locked-mode hover reveal and the interactive buttons are unaffected

> Verification: the **real plugin sources** (`teleprompter.ts` / `musicView.ts`) plus the **real `styles.css`** executed in Playwright + Chromium — **34 assertions passing, 0 page errors**: 22 for the teleprompter (toolbar always 1 row, window width = floor, floor = single-line width + 4, narrow-window wrapping premise, old 240px floor raised, long content still driving the width, click-through lock on/off, legacy narrow locked width, no re-layout on font change while locked, drag limits, 300px-viewport degradation, two lyrics-mode double-clicks going "play → pause", line-mode double-click still jumping without toggling playback, click-through lock hit-testing) and 12 for the music panel (cover overlay icon following the play state, backdrop measured via `getComputedStyle` to be the darkened cover rather than an accent colour, always-visible audition marker, overlay click toggling playback instead of stopping, `stopPreview` resetting and fading out, clicking "preview" switching to the lyrics pane with a "loading preview…" status and auto-matching + temporary mounting once playback starts)

#### 1.1.2 (2026-10-04)

**New features**

- **Frosted glass for the teleprompter background**: the panel now blurs and saturates (`saturate(1.4)`, matching the highlight-index card's hover look) the editor content beneath it via `backdrop-filter` — pair it with a lower background opacity for the desktop-lyrics frosted look. Two new settings under "Teleprompter", right below "Background opacity": a **"Frosted glass" toggle (on by default)** and a **blur-strength slider (0–40px, default 16px, with a reset button)**. The implementation follows the teleprompter's "CSS variables + class toggles" convention — the toggle drives an `is-glass` class on the root, the blur radius a `--tp-glass-blur` variable, and changes propagate to every instance via `applySettingsToAll()`; `backdrop-filter` was added to `.glimpse-tp-body`'s transition list so toggling eases over 0.2s. **The glass is removed automatically while "Hide Background" is active** — over a fully transparent background a borderless, colorless pure-blur rectangle would remain (blurring the content behind, looking like a smudged pane), so the two states must be mutually exclusive. Missing fields in older data.json fall back to defaults through the `Object.assign` merge — no migration needed
- **Text stroke for the teleprompter** (desktop-lyrics style, easier to read over busy backgrounds, **always active** — unlike the background-hidden drop shadow): a new collapsible "Text Stroke" settings group (same collapse interaction as "Text Shadow": `setHeading()` header + chevron) with four items. **The defaults are the tuned values: enabled, outer mode, 1px, white**
  - **Two stroke modes**:
    - **Glyph stroke** (`-webkit-text-stroke` + `paint-order: stroke fill`): the stroke's centerline sits on the glyph edge and `paint-order` tucks it **beneath** the gradient/font-color fill — the inner half is covered by the fill, only the outer half shows, and glyph weight is unaffected. `paint-order` for HTML text needs Chromium 123+ (the current Obsidian runtime qualifies); on older kernels it degrades to slightly thicker glyphs, which is acceptable. `-webkit-text-stroke` inherits, so the per-character gradient spans (`.glimpse-grad-char`) need no extra declaration
    - **Outer stroke** (an SVG `feMorphology` dilation filter): the filter chain is "`feMorphology(dilate)` expands the text's alpha silhouette → `feFlood` paints the stroke color → `feComposite(in)` clips the colored outline → `feMerge` places it beneath `SourceGraphic`" — it operates on **rendered pixels**, so gradients, per-character gradients and translucent fills all work, and the full stroke width shows (glyph stroke shows only half). The filter definition is injected into `document.body` by `TeleprompterManager` at construction (a zero-size hidden `<svg>`; a single shared definition suffices since width/color are global settings) and removed wholesale on plugin unload; `feMorphology`'s `radius` and `feFlood`'s `flood-color` are SVG attributes rather than CSS, so `applySettingsToAll()` syncs the filter parameters via JS **before** switching window classes to avoid referencing stale values; the filter region is padded by 50% (the default 10% margin would clip the dilation on short content). Known trade-off: the dilation kernel is rectangular, so diagonal stroke corners look slightly squarish at large widths
  - **Width slider 0–12px** — glyph stroke shows about half the value, outer stroke the full value (noted in the setting's description); **color** is a palette whose "Clear" restores the default white — `null` now means "default stroke color", with the fallback unified in the `DEFAULT_STROKE_COLOR_VALUE` constant (aligned across applySettings, the filter's `flood-color`, and the CSS variable fallback so a reset can never turn the stroke black again)
  - **Stacking with the drop shadow**: `filter` is a single property and two rules would override each other entirely, so "outer stroke + hidden background + shadow on" is merged into one `url(#…) drop-shadow(…)` rule; shadow-off and placeholder states have their own fallbacks (placeholders stay lightweight with no filter, and `:not(.is-placeholder)` keeps the merged rule from fighting the lightweight rule on specificity)
- **Music downloads: automatic platform-cookie renewal write-back (Cookie JAR)** (completed in the previous iteration, shipped with this release): a platform cookie pasted by hand from the browser's F12 panel is a static string — NetEase's `MUSIC_U` and QQ's `qm_keyst` are both HttpOnly and invisible to `document.cookie`, so when the platform renews the credential through its responses, the local copy stays stale and eventually "expires", forcing another round of manual copying. A dedicated `cookieJar.ts` now parses `Set-Cookie` from response headers and merges it back into the locally saved cookie, gated by a **double whitelist of hosts and cookie names** (so platform A's credential can never land under platform B, and tracking/AB garbage cookies never pile up in data.json); **deletions never land** (`Max-Age=0` / expired cookies are ignored, so one platform-side cleanup sweep can't wipe the pasted credential); renewal timestamps are stored in `platformCookiesUpdatedAt`. Each platform's cookie-row status badge in the settings is now computed live: "configured (N chars)", gaining "**auto-renewed MM-DD HH:mm**" once a renewal has landed; re-pasting or clearing manually invalidates the previous renewal marker. The request side was tightened in the same pass: transport markers such as the platform tag are used only to locate the platform and are stripped from outbound headers
- **Font-picker modal: Cancel/OK moved to the header row**: the modal is small and bottom-placed buttons required scrolling to the very end to confirm. They now share the header — title on the left, Cancel/OK on the right (OK as CTA) — visible the moment the modal opens no matter how long the list; removing the old bottom action row also saves one line of height. Confirm/close logic and the Esc-to-cancel behavior are unchanged

**Bug fixes**

- **Fixed "teleprompter background far wider than its content (width/content drift)"**: the typical symptom is a background spanning the whole viewport around a single centered line of text with vast empty margins on both sides. Investigation confirmed the window was **not** width-locked (`widthLocked: false`); there were two root causes. **First**, width fitting had exactly one trigger — the async Markdown render completion callback — and when that callback was skipped (a render race where `renderSeq` supersedes an older render, a hung render, or an exception), the width stayed at its stale value forever with no self-healing anywhere in the chain. **Second**, the natural-width measurement cloned the toolbar buttons into the probe alongside the content, but the cloned buttons are block-level boxes that stack vertically — measuring neither the real single-row toolbar width (~530px) nor keeping the toolbar from inflating the window. The fix restructures the feature as "**CSS-native hugging + multi-trigger refitting**", so the visible result no longer depends on the measurement being right:
  - **The visible panel uses `width: fit-content` to hug its content**: the background panel wraps the text itself (capped by `max-width: 100%` at the root width so long text still wraps; `min-width: 240px` matching the root so very short lines stay grabbable). Even if the width state drifts due to an async glitch, the visible background never shows large blank areas; **width-locked (`is-width-locked`) and mid-resize (`is-resizing`) states fill the root width** — the user's chosen width takes effect and the panel follows the handle during drags, preserving live resize feedback
  - **The root window is now `pointer-events: none`**, with only the visible panel/toolbar/resize handle set back to `auto`: a drifted, oversized transparent area can no longer intercept clicks meant for the editor underneath; drag/wheel handlers on the root still work via bubbling from children, the `:hover` chain reaches ancestors through child hits (toolbar hover-show and locked hover-show behave as before), and the mode menu's `mouseleave` close still fires
  - **The resize handle moved from the root onto the panel body**: it now always sits on the visible panel's right edge rather than on a possibly-drifted window edge; during a drag `is-resizing` temporarily stretches the panel to the root width so it follows the mouse
  - **The measurement measures content only**: the toolbar no longer participates in width calculation and instead wraps via `flex-wrap: wrap + max-width: 100%` (centered rows, gap kept) — when the window is narrower than the toolbar, the hover toolbar wraps into multiple rows instead of widening the window
  - **Multi-trigger refitting**: beyond the render callback, three fallbacks were added — (1) a `ResizeObserver` on the content area (catching late box changes: late font loads, theme switches, per-character gradient re-wrapping, late async writes); (2) a viewport resize listener (the clamp result follows the available width); (3) a once-per-second reconciliation (any missed trigger self-corrects within 1s). Two anti-flicker guards: a `renderSettled` flag skips fitting while an async render is in flight (measuring the partial content right after `contentEl.empty()` would make the width oscillate), and everything yields during `is-resizing` (the drag writes the root width directly; refitting would steal it back)
  - Verified: the real drift scenario (state width 1392px vs content ~900px at 32px font) converges immediately after reload; style regressions checked across the background-hidden / click-through-locked / placeholder / per-character-gradient combinations (the placeholder-lightweight rule vs. the outer-stroke filter rule specificity relationship, the `:hover` chain, and locked-mode button visibility all keep their original behavior)

#### 1.1.1 (2026-10-02)

**New features**

- **New "Regex find & replace" module (the headline of this release, ported from [bongho/obsidian-regex-replace](https://github.com/bongho/obsidian-regex-replace))**: regex search, replace and replace preview inside the current note (or the selection). Three entry points: the command palette's "打开正则替换 / Open regex replace", the note body's context menu "正则替换…" (lucide `regex`), and **`Ctrl+H`** in the editor — which is exactly the default hotkey of the core "Replace" command, and since Obsidian does not assign a plugin's default hotkey when it conflicts with an existing command (a `hotkeys` declaration is ineffective), the takeover is done with a window-level capture-phase keydown listener that stops propagation. The takeover conditions are deliberately narrow (editor context only, exactly Ctrl+H with no extra modifiers, never during IME composition, never while another modal is open, never on macOS — Cmd+H is the system-level "hide window"); every other case falls through to the native behaviour, and the native "Replace" remains reachable from the command palette or by rebinding. Inside the dialog: search pattern + replacement + three flag checkboxes (`i`/`m`/`s` — **`g` is permanently implied and not offered** — the module's semantics are "replace all", so the match count and the number of replacements always agree, avoiding the reference project's "count reports every match but only the first gets replaced" inconsistency) + "selection only" + a match-count line + a before/after preview + a match list + a history dropdown
  - **Engine**: a pure-logic layer (`src/regex-replace/engine.ts`, no Obsidian/CM dependencies) — compile failures return `{ error }` instead of throwing (shown on the count line, never clearing the input); the replacement is **computed exactly once**: `collectMatches` pre-expands each match's replacement text inside the exec loop (`$1` / `$<name>` / `$&` / `$$` plus `\n`/`\t` escapes), and the preview highlighting, the editor live highlight, the actual write-back and the replaced full text all derive from that one `MatchInfo` list — there is no room for "the preview runs one algorithm, the replacement runs another" divergence (which also tightens the reference project's split of "hand-written expansion for the preview, native `replace` for the apply", whose edge cases — e.g. `$2` referencing a non-existent group — behaved differently); the expansion is computed from the exec result rather than by re-running the regex on the matched substring (re-running loses surrounding context, so lookbehind/lookahead would take effect at wrong positions and the preview would lie); empty matches never advance `lastIndex`, so the loop bumps it by hand to avoid hanging. Verified: 26 assertions pass (capture groups / named groups / `$$` / `$&` / escapes / lookbehind / zero-width matches without a hang / i·m flags / invalid regex returning an error / the preview agreeing with the per-match replacement exactly / the three preview-window cases / monotonic match offsets)
  - **Replace preview**: the "before" view lights up every match inside a clipped window and the "after" view colors alternating "kept as-is / produced by the replacement" slices — a 1000-character budget anchored on the first match (the "after" view anchors on the first change with 200 characters of leading context), so large documents are never rendered whole; truncation points show an ellipsis and the view scrolls to the first highlight (`block: nearest`, staying calm while typing); the match list shows the first 10 `"match" → "replacement"` pairs, folding the rest into "…N more"; **both the highlighted fragments and the list items are clickable** — the cursor lands on that match, it is scrolled to the middle of the viewport (only `cm-scroller` moves), and the dialog then closes to yield the editor
  - **Live match highlight in the editor**: while the dialog is open, the search hits light up inside the editor itself (`src/regex-replace/highlight.ts`, a StateEffect + StateField of the same shape as the reader highlight: cross-line matches are split per line into mark decorations, with the colors in styles.css so user CSS snippets can override them); it refreshes as you type and clears when the dialog closes — nothing persisted, nothing in the undo stack, and stale matches never linger through subsequent edits; capped at 1000 matches, the same magnitude as the selection highlighter
  - **Write-back strategy**: unlike the reference project's whole-document `setValue`, replacements are dispatched as "one match = one change" in a batch — a single transaction is a single undo step, the cursor and selection are mapped by CM automatically, content outside the selection is untouched, and matches whose replacement equals their text are skipped so the undo stack stays clean; in "selection only" mode coordinates are offset by the selection start, and an empty selection is refused explicitly instead of silently widening to the whole note
  - **History**: successful replacements are stored deduplicated by "pattern + replacement + flags" (adjustable cap, 0 = off); the dropdown at the bottom of the dialog fills the inputs back in and resets its own placeholder, so the same entry can be picked twice in a row
  - **New "正则替换" settings tab**: preview toggle, history-limit slider (0–50), clear history, and an entry button; the data lives in the `regexReplace` field of data.json
  - Opening the dialog with a short selection (<100 characters) pre-fills the pattern with the escaped selection (the "fix this word" scenario in one step); pressing Enter in either input triggers the replace immediately (Enter during IME composition is never stolen)
- **Reading aloud: "Generate audio file"** — select text → right-click "朗读：生成音频文件" (lucide `file-audio`, the item only appears with a non-empty selection) or the command "朗读：生成音频文件（选区）", and the selection is synthesized through the **same segmentation chain the reader uses** (the same Markdown filtering rules and segmentation parameters, the same engine routing and config gate — a missing GPT-SoVITS reference audio is refused right away with guidance) and saved as **one** audio file, not a folder of segment fragments
  - **Multi-segment joining**: a single segment is written as-is with no repacking (zero risk for the common short selection); multiple WAV segments are repacked by parsing the RIFF chunks — the first segment's fmt chunk is copied verbatim as the header (extension fields included), the PCM streams are concatenated in order, and matching sample rate / bit depth / channel count is verified explicitly, so an inconsistent set errors out instead of producing a broken file; stream containers such as OGG are concatenated byte-wise (OGG chaining is standard semantics — players play the logical streams back to back). Verified: 19 assertions pass (header fields preserved / PCM order / RIFF size / non-canonical layouts — extended fmt and extra chunks before data / mismatched formats erroring / non-WAV erroring / the output re-parses)
  - **Save-folder setting**: the reading settings page gains a "生成音频文件" group (engine-independent, placed after the engine groups) — a "Save folder" text field plus a "Browse…" button (reusing the `electron.remote.dialog` native file-explorer dialog, anchored to the current value's directory; directory picking has no `input[type=file]` fallback, so unsupported environments are told to type the path); when left empty the file goes to the system Downloads folder
  - The file name is the selection excerpt (Windows-illegal characters and newlines stripped, 24 characters) + a timestamp; duplicates get a `-2`/`-3` suffix instead of overwriting (the same policy as reference-audio imports); writing uses a plain `Uint8Array` (Node's fs supports it natively), never relying on the renderer's `Buffer` global
  - When the service is not running it goes through the "prepare the local speech service" flow automatically (progress on the notice); synthesis failures report inference health and print the service-log tail to the console (the same pipeline as reading failures); a persistent notice shows "synthesizing segment x/n…", and completion reports the full saved path; **desktop only** (writing goes through Node fs — the command is unavailable and the menu item absent on mobile)
- **Settings: the "Highlight index" tab merged into "Selection highlighting"** — the main tab bar is back to six tabs (persistent / selection / teleprompter / music / reading / regex replace); the "Startup auto-open highlight index" toggle moved to the end of the Selection page (under a "Highlight index" section heading, following the `setHeading()` convention); the settings data structure is unchanged and saved values carry over seamlessly; the old `tabs/index-ui.ts` is deleted

**Bug fixes**

- **Fixed the regex-replace preview showing no highlighting at all** — the style rules painted the match/replacement backgrounds onto **`var(--text-highlight)`**, a variable that **does not exist** in Obsidian (verified directly against the installed app's resources: the default theme defines **`--text-highlight-bg: rgba(255, 208, 0, 0.4)`** and references `--text-highlight` zero times); CSS makes an entire declaration invalid when `var()` names an unknown variable, so the background resolved to transparent — "the class names were in the bundle, the rules were in the file, and yet nothing was visible". Fix: three rules (preview matches, preview replacements, the editor live highlight) now use "the real variable name + a literal fallback" — `var(--text-highlight-bg, rgba(255,208,0,.4))` for matches and Obsidian's idiomatic `rgba(var(--background-modifier-success-rgb, …), .3)` translucent green for replacements — so they render even when a variable is missing. Verified: styles.css passes esbuild's CSS parse (ruling out a syntax error swallowing the whole region), and a verification page built from the real styles.css with the dialog's exact DOM structure was screenshot-checked in a browser for both cases — panel A carrying the real theme variable values (the variable path) and panel B with both variables absent (the fallback path) — with "before" highlighted yellow and "after" highlighted green in both

- **"Cursor follow" now defers to whatever you are doing** — with cursor follow on, the reader used to move the cursor to the current line unconditionally on every segment or clause advance, which **destroyed the text a double-click had just selected** and also yanked the cursor away from your typing position when editing while listening. A new check (the pure function `shouldHoldCursorForUser`, so it can be unit-tested) leaves the cursor alone while the **editor has a non-empty selection** or **less than 8 seconds have passed since your last edit**, and **resumes automatically** once neither holds — there is no suspended state you have to clear by hand. The timestamps are refreshed only by **document changes** and **double-click reveals**, never by the reader's own cursor movement (otherwise the window would be renewed indefinitely and following could never resume); starting a new reading session (the segmentation baseline) clears the timestamp so following is not mysteriously inactive for the first 8 seconds right after you edit and hit read. Verified: all 11 cases in the decision table pass (including "defers inside the window, resumes once past it — it can never hang permanently"); headless Chromium with real CM6 confirms that **the selected text is left exactly as it was while following is suspended**, and a **control case** shows that the same advance with following still on does destroy the selection — proving the deferral is what saves it

**Bug fixes**

- **Fixed the teleprompter selecting an unknown paragraph when double-clicked in reader-extract mode** — double-clicking used `editor.getCursor().line` for reader mode (and only ever selected the whole line). That is the position of the **editor cursor**, while the reading position is driven by the **audio clock** and is unrelated to the cursor ("cursor follow" is off by default), so the double-click usually selected whichever line the user had last left the cursor on — the "unknown paragraph". It is now handled by the reader controller's `revealCurrent()`: it scrolls to the segment being read using the **current highlight range** and selects **exactly the text the reader highlights**, then brings the reading leaf to the front and focuses the editor (scrolling still only moves `cm-scroller` via `scrollPosToCenter`, never the ancestor containers, so the player bar cannot be pushed out of view) and finally resets with `pinBar()`. The range comes from the **same source** as the text the teleprompter displays (the newly extracted `currentSpan()`: the current clause when clause highlighting is on, otherwise the whole segment content range), so what is displayed and what a double-click selects cannot disagree. Double-clicking while nothing is being read (the placeholder) now does nothing instead of selecting something arbitrary. Verified in headless Chromium with real CM6, the real segmenter, real highlighting and the real scroll path — all 19 frames pass: the selected range equals the highlighted range, the selected text equals the rendered highlight text, the scroll offset stays in bounds, and the **old behaviour differed from the reading range in all 19 frames** (which is exactly where "an unknown paragraph" came from)
- **Fixed read-aloud highlighting drifting as a whole when the note is edited while reading** — a segment's `rawFrom`/`rawTo` are coordinates from **the moment of segmentation**: the decorations themselves map through transactions automatically (`RangeSet.map`), but every segment change, clause advance and teleprompter text read **recomputes** the range from those stored coordinates. Editing while listening therefore fed the recomputation stale coordinates — the highlight shifted by exactly as many characters as were inserted or deleted, and drifted further with every edit. The controller now accumulates the **change chain since segmentation** (`ChangeSet.compose`) and maps every coordinate through `mapPos` at the **two exits where coordinates leave the controller** (dispatching the highlight in `applyRange`, and reading text for the teleprompter in `getCurrentText`). The association **matches CM's own decoration mapping** (`from` with assoc 1, `to` with assoc -1), so the "automatic mapping" and "recomputation" paths make the same choice at insertion boundaries and the highlight no longer jumps when the segment changes. Details: a range deleted down to nothing returns `null` and clears the highlight (instead of covering unrelated text); the chain is reset at the **segmentation baseline** and **survives an editor rebuild** (switching tabs or workspaces makes Obsidian destroy and recreate the CM view, while those edits are already in the document — which is why the chain lives in the controller rather than in a `StateField`); and the "decorations were lost, re-apply them" path goes through the same mapping. All 42 checks pass (11 single-edit cases, 5 multi-edit cases and boundary cases): the recomputed range is **byte-identical** to CM's own mapped decoration, and after an edit the highlighted text is exactly the original segment text with that same edit applied

**Bug fixes**

- **Fixed "after the reading service has been running a while, every synthesis fails with `[Errno 22] Invalid argument`"** — the root cause was that starting the service wired the child process's stdout/stderr into **pipes** (`stdio: ["ignore","pipe","pipe"]`) whose read end is held by the plugin instance: reloading the plugin (hot reload, restarting Obsidian) collects the old instance and closes the read end, so the next time the service writes to stdout (tqdm progress bars, `print`) it throws `OSError: [Errno 22]` and every inference afterwards fails (both incident timelines follow a plugin hot reload; it was also reproduced deterministically by "actively destroying the parent-side stdout": 18,076 bytes succeeded before closing the read end, and the error afterwards matched character for character). They are now redirected to `reader-service.log` in the plugin folder (the parent closes its fd right after spawning), with the side benefit that logs survive reloads and "View service log" works for adopted services too (it reads the last 256KB of the file and decodes line by line to cope with GBK)
- **Fixed "on Chinese Windows some segments fail with 400: `'gbk' codec can't encode character`"** — the service `print`s the target text in several places, and with the service started as `python -I` its **stdout, redirected to a file, defaults to GBK**, so as soon as the text contains a character GBK cannot encode it throws `UnicodeEncodeError`, which bubbles up as `{"message":"tts failed"}` — looking like "random breakage" (a different note works fine). The pit inside the pit: `PYTHONIOENCODING=utf-8` is a dead end, because `-I` isolated mode implies `-E`, which **ignores every `PYTHON*` environment variable**; only the command-line `-X` is unaffected. The start arguments are now `-I -X utf8` (verified with a standalone instance on port 9881: the same request was 400 before the fix → 200 / 33,174 bytes after)
- **Fixed "clicking stop answers 'no plugin-started service to stop' and the Python process becomes an orphan"** — the launcher instance is rebuilt whenever the plugin reloads, but the Python process it spawned does not exit with it, and the rebuilt instance does not recognise that process: "it is running but nobody is responsible for stopping it". `{pid, port, startedAt}` is now persisted to `reader-service.json` in the plugin folder and the plugin **adopts** it on load (the criteria are that the PID is still alive — `process.kill(pid, 0)`, where **EPERM also counts as alive** — and that the port really is serving with a port number matching the record, to avoid PID-reuse false positives); `stop()` became "`/control?command=exit` → poll for the port to be released → kill by PID on timeout", plus a `forceStop()` (no ownership test, closes by port) and its command
- **Fixed "some voices drop everything after the first 100 characters / read only the second half"** — two overlapping root causes (measured across 7 voices × 25/50/100/150 characters): ① a **too-short reference audio** (1.5s, where upstream recommends 3–10s) makes the AR model's alignment slip, so it believes the start of the target text has already been spoken and starts reading from the middle (with the same weights and an 8-second reference, 25/50/100-character completeness settled at 83–84%); ② v2ProPlus **ends long text early (EOS)** under `cut0`, finishing generation past roughly 100 characters (at 150 characters every voice dropped to 45–72%). The per-segment limit is now tightened to ≤100, and the docs and settings guidance require a 3–10s reference audio that is **word-for-word identical** to the reference text; **leaving the reference text empty** (the no-text-prompt mode) also fixes it at the root (one voice went from 28% → 111% completeness with a short reference), so the client-side validation of an empty reference text was relaxed accordingly
- **Fixed "in-segment highlighting stops working entirely, a whole segment stays unlit, and no error is reported"** — `clauseRawSpans` could compute an **inverted range** with `from > to`, and `buildDecorations` returned `Decoration.none` outright when handed `to <= from`, so the console stayed spotless with no clue at all. The trigger is common: when a list item's/quote line's original range is stretched by Markdown marks and the segment also contains filtered characters, `rawToFiltered`'s ceil semantics slip one step outside the segment (measured: a list item `{from:158, to:95}`, a quote segment `{from:240, to:131}`). `segmentFilteredBounds()` was added as the **single anchor**: sub-range indices are clamped back to the segment bounds before conversion, and `to` falls back to no less than `from`
- **Fixed "a pure-punctuation line makes synthesis fail with 400: segment N synthesis failed… enter valid text"** — an ellipsis on its own line (`第一句。\n\n…\n\n第二句。`) produced a "readable segment" containing just `…`, which the server answers with a plain 400 for pure punctuation; the same shape occurs with `- …` in a list and with a note that is nothing but punctuation. Trailing punctuation runs are now always stripped (**excluding closing quotes and brackets** — they are part of the displayed content, and stripping them would make slicing and highlighting cut the closing quote off; and **excluding dashes**, so `——` is not stripped down to a single lonely dash), and if what remains contains no letter/digit/emoji the segment is not sent at all
- **Fixed "cross-line highlighting only looks right on the last block of each line"** — `Decoration.mark` is an **inline** decoration, so one mark spanning several lines renders as a single span across the newline, and only the last block on a line appears lit. Marks are now generated per line and empty lines produce none; the regression criterion checks with real CM6 that "no mark spans lines", "one mark per line" and "no mark on empty lines"
- **Fixed "the player bar is pushed out of view the moment the first audio starts"** — the real root cause is that CM's `EditorView.scrollIntoView(pos, {y:"center"})` **scrolls clipping ancestor containers along with it** when it cannot scroll itself, and the player bar is the first child of `.view-content`, so it gets pushed out as soon as the container scrolls (this was once misdiagnosed as a notice overlay, and service preparation/retry progress was moved into the bar itself along the way). It now uses `scrollPosToCenter()`, which only sets `cm-scroller.scrollTop` (centring and clamping itself), leaving ancestor containers entirely untouched
- **Fixed "the stop button on the right of the player bar is clipped"** — `.glimpse-reader-bar-message` lacked `min-width: 0`, and since Chinese has no spaces its min-content width equals the whole string, so a long message stretched the row wider than its container and the right-hand button was clipped by `view-content`'s `overflow: hidden` (hence only "sometimes"). `min-width: 0` and `box-sizing` were added, and `z-index` was raised to 2 to sit above `.view-header` when it floats
- **Fixed "callouts are read aloud, and the code blocks, tables and list marks inside a callout are not filtered at all"** — four symptoms, one root cause: `markFencedCode` / `markTables` / `markHeadingMarks` / `markListMarks` all test the start of a line against the **raw line text**, while structure inside a blockquote carries a `> ` prefix (`> ```js`, `> | a | b |`, `> - item`) that every regex failed to match. `quotePrefixLength()` was extracted so every line-level rule strips the quote prefix before matching and adds the offset back when characters are dropped; a new "callout markers" filter item removes `[!type]` and the fold marker attached to it while **keeping the title text**. A subtle knock-on problem was fixed along the way: the `!` in a leftover `[!note]` was treated by the segmenter as a sentence-ending exclamation mark, chopping `[!note] title` into two fragments
- **Fixed "in-segment highlighting tints the block's trailing punctuation too, and the whole-row grey background on the reading line is noisy"** — a block's trailing punctuation (including a run of it) is no longer highlighted: lighting up a whole sentence and then tinting the final "。" as well looks like one character too many is marked (the punctuation still belongs to the block and its pause still counts); the reading line's whole-row grey background was removed as well (piled on top of the in-segment highlight it also covered the gaps between segments, which was visually noisy), and the line decoration is kept as a customisable hook
- **Fixed "the hard limit's look-back cuts off a 4-character stub"** — it used to look back for spaces only, cutting a sentence in half and leaving 4 characters for the next segment (measured: "圆周率是 3.14159，见 U.S.A. 的资料。第二句在这里。" splits into `[21, 4, 7]` at a 25-character limit, and a 4-character segment costs about as much synthesis time as its audio duration — very wasteful). It is now **punctuation/newline first with spaces only as a fallback**, and the scan range includes the limit position itself (a sentence-ending punctuation mark landing exactly on the limit is taken in), giving `[26, 7]`
- **Fixed "removed URLs leave behind runs of spaces"** — `访问 [链接](url) 或看` → `访问  或看`, and those spaces are **not adjacent in the original text**, so the collapse must act on the **filtered** character stream. Only spaces/tabs are collapsed now (newlines untouched), trailing line spaces are trimmed, and mapping entries are dropped in step with dropped characters
- **Fixed "a wrong install root → `ENOENT` plus a blank wait for the full 120-second timeout"** — three real problems: the path was not pre-validated, an install archive unpacked into a **doubled same-named directory** was not located automatically, and `spawn`'s `ENOENT` arrives via the `error` event and **does not fire `exit`**, while the readiness polling only listened for `exit`, so it inevitably waited out the timeout (the most severe link). `api_v2.py` and `runtime/python.exe` are now pre-validated; probing one level down, a single hit is adopted automatically and echoed in the result as "auto-located a subdirectory" (**without writing it back to settings**), while multiple candidates are listed for the user to choose; polling records `spawnError` separately and checks it first, failing immediately (spawn can also **throw synchronously**, e.g. `EFTYPE`, so both paths must be covered). Regression covers 12 cases: a synchronous throw fails in 0.0s, an asynchronous `error` event in 1.0s
- **Fixed "CUDA is installed but Qwen3-TTS is still downgraded to CPU"** — PyTorch **does not use the system-installed CUDA Toolkit**: the Windows torch wheels bundle their own CUDA runtime, and **the torch on PyPI's default index is CPU-only** (measured: it installs `torch 2.14.0+cpu`); `qwen-tts` treats torch as an ordinary dependency, so `pip install qwen-tts` naturally pulls in the +cpu build, while `torch.cuda.is_available()` only looks at torch's bundled runtime and the driver. The flow now runs `pip uninstall -y torch` first and then explicitly installs a CUDA build from `download.pytorch.org/whl/cuXXX` (**`pip install -U torch --index-url` alone is not enough**: in PEP 440's local version ordering `+cpu` sorts after `+cuXXX`, so pip considers the installed one newer and skips it); the cu tag is tried newest to oldest against the UMD version in `nvidia-smi`'s header, falling back on failure; an existing environment whose `torch.cuda.is_available() === false` is reinstalled automatically to heal itself
- **Fixed "after a second successful probe the plugin marks its own service as external, loses track of it and `stop()` refuses to kill it"** — when `ensureRunning()`'s second probe succeeded it downgraded the state to `external`; it is now "never downgrade while a live child is still in hand" (`this.state = this.child ? "owned" : "external"`). It looks entirely reasonable when only reading the code — this was caught by running it end to end
- **Fixed "diagnostics report 'python.exe not found' while the launcher can actually locate it automatically"** — diagnostics used the raw install root the user typed, without the doubled-directory auto-location: **diagnostics and launching must share the same decision**, so `resolvePythonExecutable()` was extracted and both now use it
- **Fixed "filling in a single weight calls `/set_*_weights` unconditionally"** — the old implementation called it whenever either weight was non-empty, but **filling in only one causes a GPT/SoVITS version mismatch that makes inference fail outright**, and it also wrecked a service that had been working. It now switches only when "this run really started a new service **and** both weights are filled in"; a service already running keeps its weights, and filling in only one now produces an explicit notice and is skipped
- **Fixed "inference health and service status were conflated"** — the status row only reflected **process state** (running or not, plugin-started or not), but "the process is alive" is not "it can infer": in a broken state the port still answers 400 while the status row said "Running", misleading users. Health (`unknown`/`ok`/`broken`) was added **orthogonally** to process state, driven by **real synthesis results** (reported when a segment starts succeeding or failing, with the diagnostics' "synthesis self-check" result folded in too), and reset after starting/stopping/adopting a service (otherwise a restart would still show the stale "inference failed")
- **Fixed "error messages dropped the key field, leaving users with the uninformative 'tts failed'"** — the service returns `{"message":"tts failed","Exception":"[Errno 22] …"}` but parsing took only `message`. `Exception` is now appended too (`tts failed —— [Errno 22] Invalid argument`) — had this existed earlier, the very first round of investigation would have shown the root cause directly
- **Fixed "decoding child-process output as UTF-8 turned Chinese paths into mojibake"** — on Chinese Windows Python writes GBK to the pipe (`MyGO_千早爱音_v2pp.ckpt` → `MyGO_ǧ�簮��`). Decoding is now "strict UTF-8 first, falling back to GBK on error", and it **accumulates bytes and only splits lines at complete newlines before decoding** (otherwise multi-byte characters split across a chunk boundary are misjudged), with an 8KB defensive cap
- **Fixed "the native file dialog would not open inside Obsidian"** — `<input type="file">` does not pop Explorer on some platforms. Inspecting Obsidian's own `obsidian.asar` showed it uses `electron.remote.dialog.showOpenDialogSync`, so there is now a three-tier order (`electron.remote.dialog` → `input[type=file]` + `webUtils.getPathForFile` → scanned list + manual entry) and diagnostics report which tier is in use. Two accompanying constraints: Electron 32 removed `File.path` (43.3.0 here), so `webUtils.getPathForFile` is mandatory; cancellation is detected by listening for `window`'s `focus` (most platforms **fire no event at all** when the user cancels) and checking 600ms later whether the file list is empty
- **Fixed "importing reference audio silently overwrote the previous voice's same-named file"** — reference audio is often kept one folder per voice, so two voices both have `ref.wav`, and the import used **only the file's base name** as the target name: picking the second one overwrote the first, and switching back found the file gone. Imports now write `name-2.wav`/`name-3.wav`… when a same-named file has a different size, and only overwrite in place when the size matches (i.e. it is the same file), so re-importing the same audio does not pile up copies
- **Fixed "the between-segment pause regressed: prefetch was switched off wholesale on the non-streaming path"** — `prime()` used "was a `streamSource` closure passed in" as the streaming flag, while the controller **always** passes that closure (returning `null` when streaming is off), so prefetch was switched off entirely and the pause between segments grew to a whole synthesis time; it now decides per segment from the return value (`isStreamed()`) with a regression case added. This also fixes a crash where `prime()` started at `cursor + 1`, **skipping the current segment itself**, so `await item.audioPromise!` got `undefined` (the window is now `[cursor, cursor + lookahead)` with an idempotent `ensureAudio(index)` extracted)
- **Fixed the misleading "the first `getVoices()` returns 0 voices" verdict in environment diagnostics** — the voice list was queried before `speak()`, concluding "0 voices" and making users think browser voices were unavailable, when in fact **`speak()` still produces sound** — Chromium fills its voice list **asynchronously**. It now queries once before and once after `speak()`, and records each boundary's name, `charIndex`/`charLength` and relative timing (the latter is exactly the data word-by-word highlighting needs)
- **Fixed "line-switch detection in lyrics/reading highlighting lagged half a beat"** (the Reading extract mode benefits too) — line-switch detection relied solely on the audio's `timeupdate` (~250ms granularity), lagging a full event cycle at worst, which reads as "a beat behind"; while playing, a separate `requestAnimationFrame` loop now reads `currentTime` directly and pushes the line switch within the next frame after the timestamp is crossed (~16ms; rAF pauses when the window is hidden and the `timeupdate` pipeline takes over)
- **Fixed "direct element style assignment" for plugin review compliance (`obsidianmd/no-static-styles-assignment`)** — every **static** inline style assignment was cleaned up one by one: the `position`/`left`/`opacity` of the Reading module's off-screen `<input type="file">`, the Qwen voice-description input's `width: 100%`, and the all-literal `style.cssText` on the teleprompter's measurement probe and clone container now all go through `setCssProps` (the interface this rule explicitly endorses, consistent with its existing use in the settings-page export and the font palette); dynamically computed values (drag coordinates, progress-bar width, slider positions, …) are runtime calculations by nature and outside that rule's scope, so they stay as they are
- **Fixed "`globalThis` usage not complying with the plugin review rules (`obsidianmd/no-global-this`)"** — the Reading module's capability probes for `require` / `process.platform` / `process.versions` went through `globalThis` and now all use `window` (consistent with the Music module's existing `(window as any).require(...)`, and friendlier to popout windows)
- **The reader settings tab now distinguishes rows by whether they need width** — **text-field rows span the full row**: service address, install root, reference-audio folder, reference audio, reference text, GPT / SoVITS weights, model folder, Python interpreter, PowerShell path, voice name and voice description (measured: those inputs were 170px, now 1076–1145px, so paths are finally fully visible); **buttons, dropdowns, sliders and toggles keep Obsidian's native compact layout** — service status, "Validate install root", "Run diagnostics", "Start local service", reference-audio language, reading language, output format, speed, lookahead, everything under the Segmentation heading, the content-filter phrase fields, and so on, so the information density matches the original. - **The separate "Apply voice" setting was merged into the "Voice" row — and it now really is automatic** — it used to be its own row, which suggested that editing the weights would take effect on its own; in fact the weights are not part of the per-request parameters, so editing the settings leaves a running service untouched. The "Voice" row now carries both "Choose voice…" and "Apply to service", with one merged description; and **editing the weight fields now hot-switches automatically (silently) whenever the two names pair up** (same-named `.ckpt`/`.pth`, 900ms debounce) — a non-matching pair is left alone, with "Apply to service" as the forced path. - **Fixed the directory inputs in the Music settings being squeezed to a sliver** — the "Audio folder" and "NetEase client cache folder" rows have very long descriptions, and the default layout puts the control on the same line to the right of the description: the long text shrank `.setting-item-control` down to its min-content, leaving the input about 140px wide (worse in narrow windows) and the path essentially invisible.
